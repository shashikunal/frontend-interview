# What does the collapsed Range guard look like in practice, and when does it matter?

> **Category:** DOM Advanced APIs | **Difficulty:** Hard | **Question #9583**

## Overview

range.collapsed is true when both boundary points coincide; guarding extraction and highlight flows on it prevents empty-mark artifacts and zero-length moves.

Creation: document.createRange() (legacy-friendly) or new Range(); both start collapsed at (document, 0).

Boundary points: a range is defined by startContainer/startOffset and endContainer/endOffset. Offsets mean CHARACTER indexes inside Text/Comment nodes but CHILD INDEXES inside Elements, the single most common source of off-by-one bugs when mixing node types. collapse(toStart) merges both points; collapsed reads true when empty.

Setting spans: setStart/setEnd(node, offset) place points directly; setStartBefore/After and setEndBefore/After anchor relative to nodes; selectNode(el) includes the element itself (points land in its parent) while selectNodeContents(el) spans only its children.

Content operations: extractContents() removes and returns a DocumentFragment (move semantics); cloneContents() copies without mutating; deleteContents() removes; insertNode(node) inserts at the start boundary splitting text as needed; surroundContents(wrapper) wraps but THROWS when the span partially crosses element boundaries, so extract-append-insert is the robust general pattern.

Geometry: getBoundingClientRect() returns the union box of rendered contents and getClientRects() the per-line boxes, the precise way to position tooltips, mention menus, and formatting toolbars over selected TEXT rather than whole elements.

Liveness: ranges adjust automatically as surrounding DOM mutates, collapsing when their content disappears, which keeps editor anchors usable across edits but means stored ranges may silently point elsewhere after heavy restructuring.

Member reference: setStart/setEnd(node, offset) place boundary points directly; setStartBefore/setStartAfter/setEndBefore/setEndAfter anchor relative to sibling nodes; selectNode(el) includes the element itself while selectNodeContents(el) spans only its children; cloneRange() duplicates; compareBoundaryPoints(how, sourceRange) orders ranges; intersectsNode and containsNode test overlap; createContextualFragment(html) parses markup at the range location.

Boundary semantics deep dive: offsets index CHARACTERS inside Text/Comment nodes but CHILD INDEXES inside Element nodes, so setEnd(el, 3) means "before the fourth child", not three characters in; mixing the two conventions is the canonical off-by-one bug when spanning mixed content.

Content operation nuances: extractContents splits Text nodes at boundaries, leaving shorter neighbors behind; insertNode places at START and leaves the range containing the insertion; surroundContents throws WrongDocumentError-style failures on partial element crossings, hence extract-append-insert as the general wrapper; deleteContents merges adjacent text nodes only in some engines.

Geometry notes: getClientRects() returns one rect per line box, letting you underline arbitrary wrapped spans precisely, while getBoundingClientRect unions them for simple tooltip anchoring; both force layout, batch reads.
