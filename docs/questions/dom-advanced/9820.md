# How would you describe Selection direction and collapsed states to a teammate?

> **Category:** DOM Advanced APIs | **Difficulty:** Medium | **Question #9820**

## Overview

direction ("forward", "backward", "none") tells how anchor relates to focus; type is "Range" for real selections or "Caret"/"None" otherwise. Backwards selections matter for tools that trim trailing whitespace differently per side, and type==="None" occurs in some browsers when selection lives inside non-editable shadow roots, worth guarding before calling getRangeAt(0).

Access: window.getSelection() returns the document’s live Selection; there is no constructor.

State properties: anchorNode/anchorOffset mark where selection BEGAN, focusNode/focusOffset where it ends (anchor after focus encodes backward selection), isCollapsed distinguishes bare carets from spans, type is "Caret", "Range", or "None", direction is "forward", "backward", or "none", and rangeCount counts contained Ranges.

Methods: getRangeAt(0) materializes the span as a Range; addRange(range) after removeAllRanges() sets selection programmatically; collapse(parentNode, offset), collapseToStart/End, extend(node, offset), setBaseAndExtent, selectAllChildren(el) cover caret surgery; toString() extracts plain text; containsNode(node, allowPartialContainment) tests membership.

Reactivity: document fires selectionchange whenever the caret or highlight moves, including between editable hosts; handlers should debounce before measuring because dragging produces rapid bursts.

Gotchas: clicking buttons steals focus and collapses selections, snapshot the Range beforehand and restore via addRange; Firefox reports type "None" for selections confined to certain non-editable contexts; shadow-DOM internals surface only through composedPath-aware code; iOS selection handles behave erratically with programmatic collapse.

Practical tips: floating toolbars position from sel.getRangeAt(0).getBoundingClientRect(); copy/share flows trim toString() before use; editors persist selection Ranges across renders to restore cursor positions.

Member reference: removeAllRanges() clears; addRange(range) installs exactly one range outside editors; getRangeAt(i) throws IndexSizeError past rangeCount; collapse(parent, offset), collapseToStart/End plant carets; extend(node, offset) moves focus keeping anchor; setBaseAndExtent sets both endpoints atomically; selectAllChildren(el) wraps a subtree; containsNode(node, allowPartialContainment) queries membership; toString() extracts plain text.

Editing contexts: inside contenteditable hosts selections drive legacy execCommand and modern beforeinput interception alike; selectionchange fires even as focus moves BETWEEN editable regions, so re-check which host owns the selection via anchorNode.getRootNode().

Browser quirks: Firefox exposes type None where Chrome reports caret-like states for control selections; Safari sometimes needs the container focused before programmatic addRange sticks; double-click word and triple-click block selections produce multi-element ranges whose toString includes block separators inconsistently.

Practical recipes: quote sharing debounces selectionchange about 150ms, requires !isCollapsed plus trimmed text, then positions UI from getRangeAt(0).getBoundingClientRect(); editors snapshot Range clones before re-rendering and restore afterwards.

See also: Range for span operations, the contenteditable attribute, beforeinput events for edit interception.
