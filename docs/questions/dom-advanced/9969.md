# What never belongs in localStorage — walk through your complete answer.

> **Category:** DOM Advanced APIs | **Difficulty:** Medium | **Question #9969**

## Overview

Any JavaScript-reachable token (JWTs, API keys) in localStorage is readable by every injected script, turning one XSS into full account takeover; cookies flagged HttpOnly exist precisely for that reason. Also avoid unbounded caches, PII regulated by policy, and anything needing integrity guarantees, storage has none. Prefer memory + HttpOnly cookies for secrets, IndexedDB for large structured data.

Interface: getItem(key) returns the string or null; setItem(key, value) coerces EVERYTHING to strings (objects become "[object Object]" unless JSON.stringify-ed first); removeItem(key), clear(), key(index), and length complete the surface; access is synchronous and main-thread bound.

Scoping: localStorage persists per ORIGIN across tabs and browser restarts; sessionStorage lives per TAB and dies with it (though survives page reloads and restores), making the pair a deliberate choice: cross-tab durable state versus isolated session drafts.

Quota and errors: roughly 5MB of UTF-16 per origin per area; exceeding it throws QuotaExceededError (names vary subtly across engines) and some private modes historically threw even on tiny writes, so production writes belong in try/catch with pruning fallbacks.

Cross-tab sync: mutations broadcast a storage event to every OTHER same-origin tab (never the writer) carrying key, oldValue, newValue (null on removal), url, and storageArea, enabling logout-everywhere and theme propagation without polling; BroadcastChannel offers richer same-idea messaging.

Retention threats: Safari ITP deletes script-writable storage after 7 days without site interaction, users clear storage freely, and nothing is tamper-proof, so treat storage as a cache, version your payloads, and revalidate against servers.

Security: every injected script reads storage, so JWTs/API keys there equal account-takeover-once-XSS lands (HttpOnly cookies exist precisely for secrets); never store PII subject to policy or anything needing integrity guarantees.

Member reference: length counts entries; key(i) enumerates names in insertion order; getItem/setItem/removeItem/clear operate per area; storage events deliver key, oldValue, newValue, url, and storageArea (the mutated Storage object) to OTHER same-origin tabs only.

Quota and eviction realities: ~5MB UTF-16 per origin per area; Chrome devtools counts UTF-16 code units so CJK content halves effective capacity; Safari ITP deletes script-writable storage after 7 days without user interaction; navigator.storage.estimate() reports usage/quota where available and persist() can request immunity.

Error handling catalog: QuotaExceededError dominates, but private modes historically threw on ANY write including zero-byte, so probe once at startup rather than assuming; JSON.parse failures on read demand guarded parsing with fallback defaults.

Serialization strategy: stringify versioned envelopes ({ v: 2, exp, data }) enabling schema migrations and TTL expiry; never rely on key presence alone since removals yield null; numbers come back as strings ("42"), parse deliberately.

Privacy and security posture: storage is readable by every script in the origin, cleared fully by users, and excluded from HTTP traffic, making it wrong for secrets (HttpOnly cookies exist) yet right for UI preferences, draft text, and non-sensitive caches.

See also: IndexedDB for large structured async storage, the CookieStore interface, BroadcastChannel for tab messaging.
