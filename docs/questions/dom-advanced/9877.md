# What is the CustomEvent interface?

> **Category:** DOM Advanced APIs | **Difficulty:** Medium | **Question #9877**

## Overview

CustomEvent extends Event with a detail property carrying arbitrary data, created via new CustomEvent(type, { detail, bubbles, cancelable, composed }). Dispatch it on any EventTarget with dispatchEvent, and listeners read event.detail. It is the built-in pub/sub primitive for decoupling modules, web-component APIs, and third-party hooks without importing a messaging library.

Construction: new CustomEvent(type, { detail, bubbles, cancelable, composed }) extends Event with an arbitrary detail payload; defaults are bubbles/cancelable/composed false and detail undefined, the classic reason ancestor listeners never fire and payloads read undefined.

Dispatch semantics: target.dispatchEvent(event) invokes listeners SYNCHRONOUSLY on the calling thread in registration order (capture phase first when bubbling); all handlers complete before the next statement runs, and listener exceptions propagate to the dispatcher rather than being swallowed.

Veto channel: with cancelable true, any handler calling event.preventDefault() flips event.defaultPrevented and makes dispatchEvent return false, letting emitters learn consumers blocked the action; without cancelable the calls are inert and dispatch always returns true.

Routing: bubbles climbs ancestors enabling delegated listeners; composed additionally crosses shadow boundaries with retargeting to the host; event.composedPath() exposes the true propagation chain either way.

Payload caveat: detail passes by REFERENCE within the same realm (no structured clone), so mutating dispatched payloads leaks into other listeners; clone defensively when fan-out exists. Cross-realm messaging needs postMessage instead.

Design tips: namespace types ("cart:item-added"), attach listeners BEFORE dispatching (late subscribers miss synchronous events), and move heavy work out of handlers via queueMicrotask to avoid stalling dispatchers.

Member reference: event.detail carries the payload by reference within the realm; composedPath() lists propagation nodes; preventDefault()/defaultPrevented participate in the cancelable contract; type mirrors the constructor name.

Dispatch ordering deep dive: capture-phase listeners run top-down when bubbles is true, then target listeners in registration order, then bubble phase bottom-up; exceptions in any handler abort subsequent handlers AND propagate to dispatchEvent caller, so wrap risky emitters in try/catch or isolate listeners internally.

Design patterns: namespace event types ("cart:item-added") to avoid collisions; register subscribers BEFORE first dispatch since delivery is synchronous (late joiners miss history); fan-out payloads should be frozen or cloned because listeners share references; heavy reactions belong behind queueMicrotask so dispatchers never stall.

Cross-realm boundary: CustomEvent does NOT cross frames/workers; use postMessage with structured clone, reserving CustomEvents for same-window coordination such as web components emitting state to pages.

See also: EventTarget as the minimal bus base class, MessageChannel and postMessage for cross-context messaging.
