# Rapid fire: explain element upgrades and whenDefined in depth.

> **Category:** DOM Advanced APIs | **Difficulty:** Easy | **Question #10500**

## Overview

Markup parsed BEFORE define() creates elements that sit unupgraded until registration upgrades them retroactively, firing constructor and connectedCallback then. customElements.get(name) returns the class or undefined, customElements.upgrade(node) force-upgrades subtrees, and customElements.whenDefined(name) returns a promise, letting code await availability before interacting, crucial when scripts load in uncertain order.

Registry API: customElements.define(name, constructor, options?), customElements.get(name), customElements.upgrade(node), and customElements.whenDefined(name) returning a promise for load-order safety.

Naming: names MUST contain a hyphen (kebab-case) keeping them clear of future platform tags; invalid names throw InvalidCharacterError, redefining an existing name throws NotSupportedError, so guard dynamic definitions with get() checks.

Lifecycle: constructor runs at UPGRADE time and may create shadow roots and private state but MUST NOT read attributes or children (they are not applied yet) nor throw; connectedCallback fires on insertion (render/subscribe here), disconnectedCallback cleans up, adoptedCallback signals document moves, and attributeChangedCallback(name, oldValue, newValue) fires ONLY for names returned by static observedAttributes.

Upgrades: markup parsed before define() sits as inert unknown elements until registration upgrades retroactively, running constructors then; customElements.upgrade(subtree) forces the pass, and awaiting whenDefined avoids interacting with unupgraded shells.

Customized built-ins: define("my-btn", MyBtn, { extends: "button" }) with <button is="my-btn"> rides native semantics (form participation, a11y) but Safari historically declined support, so feature-detect before relying on it.

Gotchas: throwing constructors brick rendering into inline unknowns; attributeChangedCallback also fires for changes made DURING parsing before connectedCallback, order guards accordingly; defining the same class under two names is allowed but rarely wise.

Member reference: define(name, ctor, options?) registers with { extends } for customized built-ins; get(name) returns undefined before registration; upgrade(node) force-upgrades subtrees containing matching unupgraded elements; getName(ctor) reverse-looks-up a registered class; whenDefined(name) resolves once available, perfect for gating enhancement code behind script load order.

Lifecycle ordering deep dive: attributeChangedCallback can fire BEFORE connectedCallback during parser-driven upgrades (attributes exist before insertion), so guard renders that depend on children; moving an element between containers fires disconnected+connected without reconstruction; document.adoptNode triggers adoptedCallback only across documents.

Constructor contract specifics: no attribute reads/writes, no childNodes inspection, no throwing; create and populate the shadow root early if used; queue microtasks sparingly since upgrades can happen mid-parse where layout is unstable.

Error catalog: NotSupportedError for duplicate names or invalid extends mapping; InvalidCharacterError for hyphen-less names; Safari historically ignored customized built-ins entirely, feature-detect via HTMLButtonElement.prototype.attachShadow-era checks or stick to autonomous elements.

See also: ShadowRoot for encapsulation, ElementInternals for form integration without shadow overhead.
